# 云函数调研存档（多 Provider 路线）

> 2026-07 沉淀。归档自 `_todo/` 多份调研 TODO 的合并结论，用于替代为知笔记作为 Memocast 默认同步/账号形态。

> 2026-08 复核结论：候选优先级调整为 **uniCloud > Supabase > magic-api > Sealaf/Lafyun**。
> 统一目标不是绑定某个平台，而是先定义平台无关的 HTTP 同步协议，再用 Provider 适配不同后端。

## 1. 调研动机

- WizNote 当前在主项目 `src/utils/api.js` 内以两个对象 `AccountServerApi` / `KnowledgeBaseApi` 直接拼 URL，baseUrl 由模块级变量 `let` + getter/setter 控制，与 store、IPC、数据库层强耦合。
- 一旦为知笔记收紧第三方客户端、调整 token 流程，迁移成本极高；希望以"云函数 provider"抽象兜底，后续 WizNote 仅是一个具体实现。
- 用户希望云函数地址**可在设置框内配置**，不写死进源代码；后续还要支持登录、文件上传。

## 2. 候选方案对比

| 方案 | 客户端 SDK | 调用形态 | 学习成本 | 数据落点 | 当前定位 |
| --- | --- | --- | --- | --- | --- |
| **uniCloud + vk-router** | 可不用 SDK，HTTP URL + Axios | 单 router 云函数路由模式（1 个云函数 = N 个 API） | 中 | 阿里云 / 腾讯云 / 软件版 | **首发方案；国内生态、阿里/腾讯适配和 uni-app 生态带来的传播价值** |
| **Supabase** | REST / PostgREST / supabase-js / Edge Functions | PostgreSQL + Auth + Storage + Edge Functions | 中 | 托管或 Docker 自托管 | **第二实现；SQL、可迁移性和长期数据底座** |
| **magic-api** | Axios / 普通 HTTP | Java 服务中的可视化脚本 + SQL API | 低（Java 用户） | 自带 Spring Boot 所连接的数据库 | **Java/SQL 扩展层；统计、管理、修复和内部 API** |
| **Sealaf / Lafyun** | SDK 或普通 HTTP | TypeScript 云函数 + MongoDB/Redis | 低 | 自托管 | **开源备选；只有在运维投入可接受或官方托管成熟后再进入 PoC** |
| **自建 Express + JWT** | Axios | 普通 REST | 低 | 自建 DB | 兜底方案，不作为近期优先级 |

**选定**：多 Provider + 统一 HTTP 协议，首发仍为 uniCloud + vk-router（URL 化形态）。理由：

1. 单 router 云函数路由模式与现有"按模块拆分 API"的思路吻合；
2. url 化后前端可完全脱离 unicloud 客户端 SDK 用 axios 调用，等于"普通 REST"，后续随时能切换到 lafyun 或自建；
3. uniCloud 同时覆盖阿里云和腾讯云，且非 uni-app 应用可通过 HTTP URL 调用云函数；
4. Supabase 为 PostgreSQL + Auth + Storage + Edge Functions 组合，适合作为第二后端和可迁移数据底座；
5. magic-api 不承担主同步后端，专门吸收 Java/SQL 开发能力；
6. Sealaf/Lafyun 保留开源路线，但暂不让其运维成本反过来拖慢主线。

## 3. 首发方案：uniCloud + vk-router URL 化

### 3.1 客户端调用形态

vk-router 在云端开启 url 化后，云端 URL 形如：

```
https://<appid>.bspapp.com/http/router/<service>/<module>/<action>
```

前端 `vk.callFunction` 等价于：

```js
axios({
  method: 'POST',
  url: 'https://<appid>.bspapp.com/http/router/user/kh/login',
  headers: {
    'content-type': 'application/json;charset=utf8',
    'uni-id-token': token,            // 登录后由云函数返回
    'vk-appid': '__UNI__XXXXXX',
    'vk-platform': 'h5'               // 或 'electron' / 'app-plus'
  },
  data: { username, password }
})
```

### 3.2 单 router 云函数路由模式

- 一个名为 `router` 的云函数作为总入口；
- 其内部按 `url` 分发到 `service/<module>/<action>`；
- 公共代码放公共模块，避免 N 个云函数重复样板；
- 客户端侧不需要 import 多个云函数对象，所有调用都走 `cloud.invoke(name, data)`。

### 3.3 前端所需依赖

调研结论：**不引入** 第三方云函数客户端 SDK。

- 理由 1：vk 客户端 SDK 依赖 `vk.appid` / `vk.platform` 在编译期注入，与 Electron + Vue2 链路耦合；
- 理由 2：本项目已用 axios，统一通过 axios 走更便于拦截与错误处理；
- 落地：`src/utils/cloud-router.js`（手写 ~110 行）+ `src/services/cloud/CloudFunctionProvider.js`（统一封装）。

### 3.4 baseUrl 与 token 在前端落点

| 项 | 存储 key | 备注 |
| --- | --- | --- |
| baseUrl | `localStorage.cloudfn.config.baseUrl` | 渲染进程可写，跨窗口同步 |
| appId | `localStorage.cloudfn.config.appId` | vk-appid |
| platform | `localStorage.cloudfn.config.platform` | h5 / electron / app-plus / mp-weixin |
| token | `localStorage.cloudfn.token` | 登录后写；登出清空 |

**不**落 `electron-store`：避免走主进程 IPC、降低 v1 接入面，后续若需要加密可再加。

## 4. Provider 分层与优先级

业务层只依赖平台无关接口：

```text
AuthProvider
NoteCloudProvider
SyncProvider
TaskProvider
```

底层 Provider 按以下顺序建设：

1. **UniCloudProvider**：首发、国内部署、uni-id、云数据库、云存储、URL 化。
2. **SupabaseProvider**：第二实现，PostgreSQL、Auth、Storage、Edge Functions；重点验证自托管与迁移。
3. **MagicApiProvider**：接入统计、运营后台、数据修复和 SQL 查询，不直接替代同步核心。
4. **Sealaf/LafyunProvider**：仅做最小兼容验证；在官方托管、镜像、备份和监控方案明确前不作为默认后端。

Provider 不向业务层暴露以下平台字段：

```text
uni-id-token / vk-appid / vk-platform
Supabase JWT / anon key
magic-token
Laf SDK 对象
```

这些字段只允许出现在 Provider 适配层。

## 12. uniCloud HTTP 调用与登录计划

### 12.1 官方能力结论（2026-08-18 复核）

uniCloud 官方支持云函数/云对象 URL 化，明确覆盖“非 uni-app 开发的系统通过 HTTP URL 连接 uniCloud、读写数据”的场景。普通云函数 URL 化后，请求会被转换成包含 `path`、`httpMethod`、`headers`、`queryStringParameters`、`body`、`isBase64Encoded` 的集成请求；因此不能把普通云函数笼统描述为“只支持 POST”。安全权限、恶意请求和 URL 化计费风险需要由业务自行控制，默认域名更适合测试，生产阶段再评估自定义域名、访问限制和抗攻击方案。

参考：

- https://doc.dcloud.net.cn/uniCloud/http.html

登录相关不建议从零实现账号密码逻辑。官方现行用户体系是 `uni-id-co` + `uni-id-common`：

- `uni-id-co` 负责注册、登录、刷新 token、登出等用户端接口；
- `uni-id-common` 供业务云函数校验 token、获取 `uid`、角色权限和自动刷新 token；
- 业务云函数 URL 化时无法自动获得完整客户端信息，应显式将 `APPID`、`PLATFORM`、`LOCALE` 等上下文传给 `uni-id-common`；
- 老版 `uni-id` / `uni-id-cf` 属于迁移兼容路线，不作为新项目首选。

参考：

- https://doc.dcloud.net.cn/uniCloud/uni-id/cloud-object.html
- https://doc.dcloud.net.cn/uniCloud/uni-id/cloud-common.html

### 12.2 登录 HTTP 形态

先验证官方 `uni-id-co` URL 化接口，不通过自定义 router 转发登录。

URL 形态（路径由 uniCloud 控制台配置，不应写死 `/http`）：

```text
POST https://<url化域名>/<uniIdCoPath>/login
```

例如控制台把 `uni-id-co` 的 URL 化路径配置为 `/http/uni-id-co` 时，才是
`https://<url化域名>/http/uni-id-co/login`；也可以配置为 `/uni-id-co`。

请求要求（这是 `uni-id-co` URL 化的专用规则，不代表普通云函数的通用规则）：

- `Content-Type: application/json`
- 方法必须为 `POST`，否则返回 `uni-id-unsupported-request`
- 不使用 Query 参数，官方说明该 URL 化入口会忽略 Query 参数
- 请求体必须是三段式结构：

```json
{
  "clientInfo": {
    "uniPlatform": "electron",
    "appId": "__UNI__COOLMA",
    "deviceId": "stable-device-id"
  },
  "uniIdToken": "",
  "params": {
    "username": "user",
    "password": "password"
  }
}
```

其中 `clientInfo.uniPlatform`、`clientInfo.appId`、`clientInfo.deviceId` 是非 uni-app 客户端需要特别补齐的字段。密码登录的 `params` 支持 `username`、`mobile`、`email` 三选一，加 `password`；连续失败达到阈值后可能需要 `captcha`。

成功响应重点：

```json
{
  "errCode": 0,
  "errMsg": "",
  "newToken": {
    "token": "...",
    "tokenExpired": 0
  }
}
```

注册、登录、刷新 token 等接口会返回 `newToken`；需要校验 token 的接口在 token 即将过期时也可能返回 `newToken`。uniCloud 客户端 SDK 会自动保存，但 Coolma 走 Axios，因此 Electron 客户端必须主动持久化新 token。

### 12.3 登录方案决策

第一版采用“两层入口”：

```text
认证入口：{uniIdCoBaseUrl}/login
认证刷新：{uniIdCoBaseUrl}/refreshToken
认证登出：{uniIdCoBaseUrl}/logout
业务入口：{routerBaseUrl}/...
```

业务 router 不重复实现密码登录，只做：

1. 读取 `uni-id-token` 或请求体中的 token；
2. 使用带 `context` 的 `uni-id-common.createInstance()` 校验 token；
3. 将 `uid`、角色、权限放入业务上下文；
4. 对 `workspace`、`notes`、`sync` 接口执行用户隔离；
5. 在响应中透传 token 刷新结果；
6. 统一把 `errCode`、`errMsg`、`newToken` 转为 Coolma 的 Provider 错误和认证结果。

`externalLogin` / `externalRegister` 暂不纳入第一轮。官方对这两个 URL 化接口要求额外的 `uni-id-nonce`、`uni-id-timestamp`、`uni-id-signature` 请求签名，后续如果要接入已有账号体系再单独评估。

### 12.4 登录 PoC 计划

#### Phase L0：只验证官方登录链路

目标：不写 Coolma 业务改造，只证明 Electron/Axios 能调用 uni-id-co。

- uniCloud 控制台创建测试服务空间；

```text

```

#### Phase L1：验证 token 生命周期

验证项：

- 使用登录 token 调用一个最小业务 `auth/me` 接口；
- 过期 token 返回什么错误；
- 接近过期时是否返回 `newToken`；
- `{uniIdCoBaseUrl}/refreshToken` 的 URL 化请求体和响应（仍使用 `clientInfo / uniIdToken / params` 包装）；
- `{uniIdCoBaseUrl}/logout` 的 URL 化行为；
- `logout` 后 token 的实际行为；
- 多设备同时登录时 token 是否互相影响；
- 本地清除 token 后是否能回到匿名状态。

交付物：

```text
access token 存储策略
refresh token/续期策略
token 失效错误码映射
登出和重新登录流程
```

#### Phase L2：接入 Coolma Provider，但不迁移同步

只新增认证适配，不改 `SyncService`：

1. 新建统一 `AuthProvider` 接口；
2. UniCloud Provider 直接调用 `uni-id-co` 的 URL 化云对象方法；
3. 将 `newToken` 统一转换为 `accessToken`、`expiresAt`；
4. 将当前 `CloudFunctionProvider` 的 token 存储改为只由认证层管理；
5. 业务请求统一携带 token，但仍保持本地优先；
6. 登录成功后只验证 `auth/me`，不自动推送本地笔记。

#### Phase L3：再接入笔记业务 router

登录稳定后，才建立：

```text
{routerBaseUrl}/system/ping
{routerBaseUrl}/workspace/current
{routerBaseUrl}/notes/*
{routerBaseUrl}/sync/*
```

所有需要登录的业务接口由 `uni-id-common` 校验 token。认证接口和笔记同步接口分离，便于后续 Supabase Provider 复用同一业务契约。

### 12.5 登录接口契约（首轮 PoC 固化）

| 项目 | 约定 |
| --- | --- |
| 登录 URL | `POST {uniIdCoBaseUrl}/login`；`uniIdCoBaseUrl` 是控制台配置的 URL 化根路径 |
| 刷新 URL | `POST {uniIdCoBaseUrl}/refreshToken` |
| 登出 URL | `POST {uniIdCoBaseUrl}/logout` |
| 请求头 | `Content-Type: application/json`；暂不依赖 Cookie |
| 请求体 | `{ clientInfo, uniIdToken, params }` |
| `clientInfo` | 至少含 `uniPlatform`、`appId`、`deviceId`；可补 `locale` 等字段 |
| 登录参数 | `params.username` / `params.mobile` / `params.email` 三选一，加 `password`；连续失败后可能要求 `captcha` |
| 成功判断 | `errCode === 0` |
| token | `newToken.token` |
| 过期时间 | `newToken.tokenExpired`，记录为时间戳并转换为 `expiresAt` |
| 失败处理 | 保留 `errCode`、`errMsg`，不要只按 HTTP 状态码判断 |
| token 持久化 | 由 Coolma AuthProvider 显式保存和替换；任何响应中的 `newToken` 都要覆盖旧 token |

