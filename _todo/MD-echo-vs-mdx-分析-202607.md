# Echo / Rune vs MDX ——一场不在同赛道的设计对决

> 写于 2026-07-29
> 目的：在动手做阶段 0 公开信之前，把"我们和 MDX 的关系"想清楚
> 立场：**不站队**，先讲清楚两者的设计哲学差异，再说有没有"斗"的可能

---

## TL;DR

**MDX 和 echo 不在一个赛道**——这是结论不是开始。MDX 是"给文档站用的 React 组件嵌入层"；echo 是"给个人笔记用的行内行为注解层"。两者表面看都是"给 markdown 加超能力"，但**目标用户、运行时依赖、使用心智都不同**。

真正的"斗"只发生在一个细分的中间地带：**带交互能力的创作工具**（带 demo 的教程、可交互博客、动态笔记）。在这个中间地带，echo 占了一个 MDX 啃不动的位置——**便携性 + 零运行时 + 自然语言**。

下面展开。

## 一、客观对比（不做价值判断）

| 维度 | MDX | Echo / Rune |
|---|---|---|
| **形态** | `<Chart data={...} />`（JSX / React 组件） | `@nice{opacity: 0.3}()`（行内注解） |
| **作用域** | 块级（嵌入整段 React 组件） | 行内（劫持附近 DOM） |
| **目标用户** | 开发者（写文档站） | 作者 / 重度笔记用户 |
| **解析方式** | 编译期（build step 必选） | 运行时（muya 解析即生效） |
| **运行时依赖** | 必须有 React / Vue / Webpack / Vite | 零——纯文本 + jQuery hijack |
| **学习曲线** | 要会 React / JSX / 组件传参 | 30 分钟：学会 `@xxx{props}()` 形态 |
| **生态** | 深（Next.js / Astro / Gatsby / Docusaurus 一等公民） | 浅（16 张内置卡片，1 人维护） |
| **可移植性** | ❌ 编译产物不能脱离构建系统 | ✅ 纯 markdown 文本，复制粘贴即可 |
| **嵌入 HTML 的支持** | 部分（通过 `mdx-components`） | 完全（echo 本身就是 DOM 劫持） |
| **典型场景** | 组件文档、API 文档、技术博客 | 个人笔记、教程写作、轻量创作 |
| **失败回退** | 构建失败 → 整页挂 | 未知 echo → graceful skip（不渲染，不报错） |
| **类型系统** | 有（通过 TypeScript 组件 prop） | 无（props 是 JSON，靠约定） |
| **CSS 隔离** | 借力 React（styled-components / CSS modules） | 借力 jQuery + global class（粗暴但快） |

## 二、设计哲学差异（这才是真正的分歧）

### 2.1 MDX 的哲学：**把 React 当作扩展点**

MDX 的核心信念是：

> "Markdown 的能力天花板是 HTML。HTML 的能力天花板是组件。所以应该直接把组件嵌入 markdown。"

这个信念的**优点**：

- 组件可以是任意复杂度——图表、表单、3D 场景、交互式演示
- 类型系统（TypeScript）可以校验 props
- 生态复用——所有 React 组件库都能直接拿过来用

**代价**：

- 必须有构建系统（Vite / Webpack / Next）
- 必须有运行时（React）
- 输出的 `.mdx` 文件**不能脱离工程环境运行**——把它复制到不支持 MDX 的地方直接报错
- 编译失败 → 整页挂，没有 graceful degradation

### 2.2 Echo 的哲学：**把 markdown 当作可编程的标记语言**

echo 的核心信念是：

> "Markdown 的能力天花板不是 HTML，而是**没有作用域的概念**。在文本里加一个'作用域声明'，让附近的节点知道'我要改你'——就够了。"

这个信念的**优点**：

- 纯文本——`@xxx{props}()` 就是普通字符，复制粘贴不丢
- 零运行时——没有构建、没有依赖
- 解析失败 → graceful skip（按 echo-rune 试验规则）
- 学习成本极低——30 分钟掌握语法，剩下就是"写卡片"

**代价**：

- 能力上限低于 React 组件——echo 不能写一个完整表单，只能写"高亮 / 折叠 / 动效"这类**行内行为**
- 类型系统缺失——props 写错只能运行时才发现
- 生态浅——16 张内置卡片，外部贡献还没起来

### 2.3 一句话总结两者分歧

> **MDX 是"把 markdown 当作 React 的宿主语言"；echo 是"把 markdown 当作自己可编程的语言"。**

MDX 的所有力量来自 React——没有 React，MDX 就是个空壳。Echo 的所有力量来自**纯文本 + 行内作用域**——没有 jQuery 也能跑，只是没那么顺手。

## 三、能不能斗？斗什么？

### 3.1 在"文档站"赛道：**MDX 完胜，echo 不要进**

现实：

- Next.js / Astro / Gatsby / Docusaurus 都把 MDX 列为**一等公民**
- shadcn / Mintlify / ContentLayer 等生态围绕 MDX 构建
- 大量现成组件（recharts、tldraw、monaco-editor）开箱即用
- 文档站用户群是**开发者**——他们已经会 React

**echo 在这个赛道完全没有位置**。我不会去竞争。诚实地讲：

- echo 没有编译时类型检查 → 在严肃文档站会被嫌弃
- echo 没有 React 组件复用 → 任何超过"行为劫持"的能力都不行
- echo 没有 build step → 不能被搜索引擎良好索引（DOM 注入的内容对 SEO 友好度差）

**结论：文档站赛道，echo 主动让位**。

### 3.2 在"个人笔记"赛道：**echo 占位，MDX 啃不动**

为什么 MDX 在个人笔记场景几乎不可用：

1. **桌面应用集成成本高**：Electron 应用集成 React + MDX 编译链 = 巨大打包体积
2. **构建 step 与即时保存冲突**：写笔记的核心是"边写边存"，编译流程不友好
3. **可移植性**：笔记导出给同事 / 朋友时，对方根本跑不起来 MDX
4. **学习曲线**：笔记用户不是开发者——让他们学 JSX 不现实

**这个赛道 MDX 进不来**，因为它的设计假设就是"工程化"。个人笔记的核心假设是"轻量、可便携、零依赖"。

### 3.3 真正能"斗"的中间地带：创作工具

这个中间地带包括：

- **带交互 demo 的教程**（如：在教程里嵌入"拖动滑块看图表变化"）
- **带 live preview 的技术博客**
- **带交互式代码片段的笔记**
- **带动态图表的科研笔记**

**MDX 在这个地带的现状**：

- 优势：能写复杂组件（图表、3D、编辑器）
- 劣势：必须工程化（Next.js / Astro），个人作者用不起

**echo 在这个地带的现状**：

- 优势：纯文本，作者写一行就能触发动效
- 劣势：能做的事有限（行内行为），做不了复杂组件

**结论**：两者**各有不可替代的位置**。MDX 做"复杂组件"，echo 做"轻量行内行为"。**真正可斗的部分**在于：

> 当一个作者只想写"高亮这一段 / 给这个段落加个动画 / 折叠这一段"时——他会用 MDX 还是 echo？

答案明显是 echo：

- 不需要装 React
- 不需要 build step
- 写一行就生效
- 纯文本，复制即用

**所以这个"斗"的结果已经定了：echo 赢**——因为这个粒度的需求根本不该用 MDX。MDX 是杀鸡用牛刀。

### 3.4 互相借鉴的空间

**echo 可以从 MDX 学什么**：

| 学什么 | 怎么做 |
|---|---|
| **自描述组件** | 把 MDX 的"组件 prop 类型"概念移植到 anno_source——给 props 加 JSON Schema 校验 |
| **组件复用** | 鼓励 echo 卡片在 npm 上发布，作者可以 `npm install @someone/echo-card-cool` |
| **mdx-components 模式** | 做一个 `echoComponents` 注册中心，类似 MDX 的全局组件映射 |

**MDX 可以从 echo 学什么**：

| 学什么 | 怎么做 |
|---|---|
| **行内作用域** | MDX 3+ 可以考虑加"行内指令"语法，类似 Vue 指令（`v-if` 这种） |
| **graceful skip** | MDX 当前组件编译失败就整页挂，可以学 echo 兜底 |
| **自然语言命名** | MDX 的 `<Highlight>` 可以考虑换成 `<强调>` 或某种 DSL 风格（但 MDX 不会真的改，那是 React 兼容问题） |

## 四、echo 的真正机会窗口

### 4.1 时间窗口

MDX 已经存在 7 年（2017 年起），生态稳固。**echo 现在不需要斗 MDX**，而是要**抢在 MDX 不进军的细分赛道里建标准**——

- 个人笔记 + 行内注解
- 创作工具 + 轻量交互
- 富文本 + 便携性优先

### 4.2 真正的对手

echo 的真正对手不是 MDX，是：

1. **HTML 内嵌**（`<details><summary>...</summary></details>`）——古老但便携
2. **块类型扩展**（Notion 的 callout / toggle）——好用但锁定应用
3. **Quill / TipTap 等富文本编辑器**——复杂但运行时重
4. **不存在的"行内注解 DSL"标准**——这是 echo 的空白机会

### 4.3 风险

| 风险 | 应对 |
|---|---|
| MDX 团队看到 echo 后决定加"行内指令"语法 | 这是 echo 的胜利——证明方向对。届时 echo 已经有 16 张内置 + SDK，先发优势在 |
| echo 30 天内没拿到 5 个反馈（阶段 0 失败） | 用户已拍板——宣告失败，转个人作品，不斗 |
| 别人做了一个更优雅的行内注解方案（如 Obsidian plugin） | 抄作业，把 16 张内置卡片移植过去 |

## 五、对外公开信中如何提 MDX

阶段 0 长文里**不要主动踩 MDX**——读者会觉得"又一个挑战 MDX 的玩具"。

正确策略：

1. **不提 MDX 名字**——专注讲 echo 的设计哲学（"行内注解 DSL"）
2. **承认 MDX 的存在**（如果有读者问）："MDX 是 React 组件嵌入层，echo 是行内行为注解层，目标场景不同"
3. **强调差异点**："MDX 不能便携使用，echo 可以"
4. **不要造"echo 取代 MDX"的叙事**——任何取代叙事都会引战，惹来 MDX 社区反扑
