# TODO — 是否升级技术栈

> 决策日期：2026-07-15
> 范围：是否将 Vue 2.7 + Quasar 1 + Element-UI + Ant-Design-Vue 1.x + Wujie-Vue2 整体升级到 Vue3 体系
> 结论先行：**不升级**。当前真实风险有更便宜的解法，升 Vue3 解决不了核心问题。
> 本文档同时是"为什么不做"的留档，也是不升级期间的具体行动清单。

---

## 0. 背景 & 关键参考规则

### 0.1 触发本决策的两个担心

| 担心 | 是否成立 | 关键事实 |
| --- | --- | --- |
| Vue2 性能跟不上 rune / echo 体系 | **不成立** | rune/echo 链路的真正瓶颈在 Muya 编辑器、DOM querySelectorAll、handler 派发；Vue 在这条链上只做"把已渲染产物挂到占位符"这一浅层工作。Vue2.7 响应式系统已用 Proxy 重写，与 Vue3 性能差异 < 5%。 |
| Vue2 生态软件安全问题 | **部分成立** | Vue2.7.16 仍在维护；真正风险在周边生态（element-ui 进入维护期、vue-i18n 8 停更）以及 transitive 依赖（lodash / jquery / ssh2 / node-schedule）。解法是 `yarn audit` + 单库评估替换，不是整栈重做。 |

### 0.2 升 Vue3 的真实成本（来自项目现状）

| 风险点 | 影响面 | 备注 |
| --- | --- | --- |
| rune 体系（`vue-template-compiler` + `Vue.extend` + `compileToFunctions`） | 全量重写 | 用户 SFC 是把 Vue 模板当 DSL 用，Vue3 的 `@vue/compiler-sfc` 产物是 VNode 函数不是字符串 render，整条 `createRuneRendererCtor` 链路必须重做 |
| wujie-vue2 → wujie-vue3 | box-im-wujie / doubao-input 子应用必须同步升级 | 主应用与子应用 Vue 版本不一致会出共享 DOM / 事件总线兼容问题 |
| element-ui → element-plus | 全 breaking | API 差异大，需逐组件改写 |
| ant-design-vue 1.x → 3.x/4.x | 全 breaking | Vue2 only 版本必须换 |
| vue-i18n 8 → 9 / vue-router 3 → 4 / vuex 3 → 4/pinia | 全栈 breaking | vuex 3 模块语法到 pinia 不是简单替换 |
| Quasar 1 → 2 | CLI / boot / 配置 DSL 全变 | `extendWebpack` 写法、`boot/` 目录结构全要改 |
| 项目体量 | 100+ 文件 + 自研编辑器扩展 + 微前端 + 同步层 + 双 UI 库共存 | 估算全职 1 人 2-3 个月，期间失去新功能迭代能力 |

### 0.3 项目真正的产品价值（与 Vue 版本无关）

| 维度 | 现状 |
| --- | --- |
| 本地优先 / 离线优先 | SQLite + dirty 字段，云端只补缺 |
| 数据所有权 | SQLite + Markdown 源本地完全可读 |
| 编辑器扩展性 | 用户能写 Vue SFC 卡片（rune）+ `@xxx{}(prompt)` 编排（echo） |
| 微前端挂载 | wujie 挂 box-im / doubao-input，独立 AI 对话、群聊 |
| AI 集成 | portkey-ai 已接入，AI 编排进 echo（生生不息 / 强运 / nice） |
| 同步模型 | dirty 字段 + 补缺式回补，规避 90% 笔记同步痛点 |

> **这些是护城河，不是技术栈。升 Vue3 不会让任何一个变强。**

## 1. 决策

### 1.1 总决策

**保持 Vue 2.7 + Quasar 1 现状。**

### 1.2 例外：单库评估替换（解耦于 Vue3）

如果某个具体库出现下列情况，**单独评估替换**，不绑定 Vue3 升级：

- 库停止维护超过 6 个月且无社区 fork
- 出现 high/critical CVE 且无修复版本
- 新功能强需求且只在 Vue3 版本中存在

当前重点观察名单：
- `element-ui` —— 已进入维护期，**新组件可单独走 Element-Plus 独立栈**，老组件保留
- `vue-i18n@8` —— 关注是否出 8.x 安全补丁
- `lodash`、`jquery`、`ssh2`、`node-schedule` —— 独立升级最新版，与 Vue 版本无关

### 1.3 升 Vue3 的"触发条件"（任一条为真再启动）

> 1. 某个核心依赖（Monaco / wujie / Muya fork）只发 Vue3 版本，且必须用它。
> 2. 招聘市场完全找不到愿意写 Vue2 的工程师，且人力成本压过迁移成本。
> 3. 计划把 coolma 从 Electron 桌面搬到 Web 端，Vue2.7 + Webpack4 成为真瓶颈。

若启动，必须按渐进迁移路径：
```
Phase 1: Vue 2.7 + @vue/compat（Vue 官方兼容垫片） → 大部分 Vue3 包能跑
Phase 2: 新组件用 Vue3 + Element-Plus，旧组件逐步迁
Phase 3: 弃用 @vue/compat，全栈 Vue3
```
每一步都必须能独立回滚。

## 4. 关键点回顾

1. **Vue 在 rune/echo 链路上只做"挂占位符"**，瓶颈在 Muya 和 DOM 操作，与 Vue2/3 无关。
2. **Vue2.7 响应式已用 Proxy 重写**，与 Vue3 性能差异 < 5%。
3. **真正的安全风险在 transitive 依赖**，用 `yarn audit` + 写法层 escape 解决，不是换框架。
4. **生态凋零是真的，但解法是单库评估替换**，不绑 Vue3 升级。
5. **项目护城河是 rune / echo / 本地优先 / wujie 微前端**，与 Vue 版本无关。
6. **只有触发条件为真时才升 Vue3**，且必须渐进迁移。
