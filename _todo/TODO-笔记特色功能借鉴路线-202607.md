## 三、按主题深度分析 · 可借鉴特色功能

下面按九个主题，分别梳理"为什么值得借鉴 + 该怎么做"。每个主题给出**借鉴强度（⭐ 数）**与**实施优先级（P0/P1/P2/P3）**。

### 3.1 架构与工程层（长期投入）

#### 3.1.1 客户端-服务端统一架构（借鉴 TriliumNext ⭐⭐⭐ + SiYuan ⭐⭐）

**为什么值得借鉴：**
- TriliumNext 即使在桌面模式下也跑 Express，前后端通过内部 HTTP/WS 通信，桌面和服务端共享同一套代码 → 直接为多端部署、移动端 Web 访问铺路。
- SiYuan 把核心数据操作做成 Go Kernel（6806 端口），桌面/移动/Web/Docker 多端共用同一个内核。
- Memocast 当前所有逻辑嵌入 Electron 主进程，无法被外部进程调用，扩展到移动端、Web 端时只能重写。

**实施路径（渐进式）：**
1. **第一阶段**：在 Electron 主进程中跑一个精简的 Express（或 Fastify）服务，封装现有 IPC handler 为 REST 路由；前端从直接 `window.api.x()` 改为 `fetch('/api/x')`。
2. **第二阶段**：引入 `@msgpack/msgpack` 或 Protobuf 替代 JSON，降低 IPC 体积。
3. **第三阶段（可选）**：核心数据层独立为 Node 子进程或 Go 二进制，桌面通过 WebSocket 与之通信，为将来 Go Kernel 化预留接口。

**优先级：P2（中期收益，长期重要）**

#### 3.1.2 TypeScript Monorepo（借鉴 TriliumNext ⭐⭐⭐）

**为什么值得借鉴：**
- TriliumNext 的 `apps/* + packages/*` 结构让前端（client / desktop）、后端（server）、编辑器（ckeditor5/codemirror）共用 `trilium-core`，类型一致、依赖清晰。
- Memocast 当前 JavaScript 主进程 + Vue2 渲染进程，跨进程实体类型靠手抄，bug 多。

**实施路径：**
- 引入 pnpm workspaces，把 `src/` 拆为：
  - `packages/memo-core`：实体模型、SQL、同步协议、加密、版本历史
  - `packages/memo-ipc`：IPC 类型契约
  - `apps/desktop`：Electron 壳
  - `apps/web`（预留）
- 主进程 TS 化通过 `tsc → dist/main` 走 Node 运行；preload 通过 `tsc` 编译到 `dist/preload.js`。
- Vue2 渲染层暂保留 JS（迁移 Vue3 见 3.4.1）。

**优先级：P2（工作量中等，长期可维护性收益巨大）**

#### 3.1.3 命令/事件总线（借鉴 TriliumNext AppContext ⭐⭐）

**借鉴要点：**
```js
// 推荐实现：轻量 EventBus（主进程 + 渲染进程各一份）
EventBus.triggerCommand('focusOnTitle', { noteId: 'xxx' })  // 向上冒泡
EventBus.handleEvent('noteSwitched', { noteId: 'xxx' })     // 向下广播
```

**为什么值得借鉴：**
- 现有 Vuex 在"跨组件无直接引用关系"的场景下捉襟见肘（如切换笔记时让侧栏、面包屑、状态栏都同步）。
- AppContext 思路可以让命令找到"唯一的处理者"，事件通知"所有订阅者"，职责清晰。

**实施路径：**
- 写一个 `EventBus.js`，提供 `triggerCommand / onCommand / triggerEvent / onEvent`。
- 关键事件：`noteSwitched`、`entitiesReloaded`、`beforeNoteSwitch`（强制 flush 保存）、`syncStatusChanged`。
- 配合 Vuex action 触发，Vue 组件用 `mixin` 或 composable 订阅。

**优先级：P1（低难度高收益）**

#### 3.1.4 前端实体缓存 froca（借鉴 TriliumNext ⭐⭐）

**借鉴要点：** 在渲染进程维护 `EntityCache = { FNote, FCategory }`，主进程变更通过 IPC/WebSocket 推送增量，组件读缓存不读 DB。

**实施路径：**
- Pinia/Vuex 中新增 `entityCache` 模块
- 主进程变更后 push `{type: 'note/update', payload: {...}}`
- 组件 mounted 时订阅 `entitiesReloaded` 事件，过滤 `componentId` 避免自更新循环

**优先级：P2（中等收益）**

#### 3.1.5 Electron 安全模型升级（借鉴 Blossom ⭐⭐⭐ P0 立竿见影）

**为什么值得借鉴：** Memocast 当前仍是 `nodeIntegration: true` + `contextIsolation: false` 的遗留配置，渲染进程可直接访问 Node API，存在 XSS → RCE 风险。Blossom 用 `@electron-toolkit/preload` + `contextIsolation: true` + `contextBridge.exposeInMainWorld` 把主进程能力按白名单暴露，是现代 Electron 的事实标准。

**借鉴代码骨架：**
```js
// preload.js
import { contextBridge, ipcRenderer } from 'electron'
contextBridge.exposeInMainWorld('api', {
  invoke: (channel, ...args) => ipcRenderer.invoke(channel, ...args)
})
```

### 3.2 数据层与存储（核心引擎）

#### 3.2.1 SQLite 性能调优（借鉴 SiYuan + TriliumNext ⭐⭐⭐ 立即见效）

**为什么值得借鉴：** 这是收益最直接、风险最小的一组改动。SiYuan 的 `journal_mode=WAL&mmap_size=2.6GB&cache_size=-2048` + 批事务是久经验证的方案。

**实施路径（落地清单）：**
```js
// better-sqlite3 初始化（替换 sql.js 或保留兼容层）
const db = new Database(path, {
  fileMustExist: false,
})
db.pragma('journal_mode = WAL')
db.pragma('synchronous = OFF')       // SiYuan 同款
db.pragma('mmap_size = 2684354560') // 2.6GB
db.pragma('cache_size = -2048')      // 2MB
// 连接池：主进程单例 + 写串行化
```

**Memocast 必做清单：**
- [ ] 切换或兼容 `better-sqlite3`（持久化、性能、FTS5 三重收益）
- [ ] 启用 WAL + mmap + 调高 cache
- [ ] 引入 `dbQueueOperation` 串行化写
- [ ] 高频写（笔记编辑）走批事务

**优先级：P0（最高，立竿见影）**

#### 3.2.2 SQLite FTS5 全文搜索（借鉴 TriliumNext PR #6839 ⭐⭐⭐）

**实施路径：**

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(

-- TRIGGER 自动同步
CREATE TRIGGER notes_ai AFTER INSERT ON notes BEGIN
  INSERT INTO notes_fts(rowid, title, content) VALUES (new.rowid, new.title, new.content);
END;
```

### 3.3 同步与数据安全（核心痛点）

#### 3.3.1 端到端加密云同步（借鉴 SiYuan ⭐⭐⭐ 强需求）

**为什么值得借鉴：** WizNote 同步目前是明文传输/存储。SiYuan 在本地用 repo key 做 AES-GCM 加密后再上传，第三方服务商拿不到明文。

**实施路径：**
1. 设置面板增加"数据仓库密钥"初始化/导入/导出
2. 同步前：content 字段 AES-GCM 加密（key 从用户密码派生）
3. 同步后：服务端只看到密文
4. 元数据（标题、标签、时间）可选择性加密
5. 支持 S3 兼容存储后端（OSS/COS/R2/MinIO）作为 WizNote 之外的选项

**优先级：P0（用户数据安全核心诉求）**

#### 3.3.2 增量变更追踪（借鉴 TriliumNext entity_changes ⭐⭐⭐）

**为什么值得借鉴：** Memocast 现有 `dirty` 字段是笔记级粒度，Trilium 是实体级（note/branch/attribute/attachment 各自独立），同步粒度更细、冲突判定更准。

**实施路径：**
- 新增 `entity_changes` 表：`id, entity_type, entity_id, change_type, hash, isSynced, created_at`
- 与现有 dirty 字段共存：dirty = 笔记级，entity_changes = 字段级
- 同步时按 500-1000 条批量推送
- content hash 判定：本地 vs 远端 hash 一致则跳过
- **Worker Thread 并行化 hash 计算**（Trilium 当前是阻塞的，可直接做出优势）

**优先级：P0**

#### 3.3.3 WebSocket 实时同步（借鉴 TriliumNext ⭐⭐）

**借鉴要点：** WizNote 服务支持 WebSocket 时，前端订阅变更事件，实时刷新笔记树。

**实施路径：**
- WizNote 服务（若有）开启 WS 通道
- 主进程作为 WS client，断线自动重连
- 重连后用 `entity_changes` 补发离线期间变更

**优先级：P2（依赖 WizNote 能力）**

#### 3.3.4 同步模式精细化（借鉴 SiYuan ⭐⭐）

**借鉴要点：** 自动（停止修改 30s 后）/ 半自动（启动退出时）/ 完全手动 三档可切换。

**实施路径：**
- 设置页增加"同步策略"选项
- 实现 `AutoSyncScheduler`：debounce 30s + 启动/退出钩子
- 半自动模式下加状态栏"待同步"提示

**优先级：P1**

#### 3.3.5 每笔记加密（借鉴 TriliumNext + Yank Note ⭐⭐）

**借鉴要点：** 敏感笔记单独加密，独立密码。

**实施路径：**
- 笔记表新增 `is_protected` 字段
- 受保护笔记 `content` 存密文，编辑器读时解密到内存
- 关闭笔记时立即清空内存中的明文
- 笔记树用 🔒 图标标识
- 加密笔记不纳入 FTS 索引（或仅索引标题）

**优先级：P2**

#### 3.3.6 3-way merge 冲突合并（借鉴 Blossom ⭐⭐⭐ P0 同步核心痛点）

**为什么值得借鉴：** Memocast 当前 `localModified` vs `serverModified` 仅做"本地覆盖"粗放逻辑，无真正冲突合并。多设备同步一旦两端同时编辑就丢数据。Blossom 通过乐观锁 + 三路合并解决。

**借鉴要点：**
- 引入 `version` 字段做乐观锁（与 SiYuan / Blossom 同思路）
- 同步前若版本号不一致，触发三路合并：
  - base：本地上次同步成功的版本
  - local：当前本地内容
  - remote：远端内容
- 段落级 diff（用 `diff-match-patch`），能自动合并就自动合并；不能合并则生成"冲突区域"
- 冲突预览 UI：左右双栏显示高亮差异，用户选 "保留本地 / 保留远端 / 手动合并"

**实施路径：**
1. notes 表新增 `version INT DEFAULT 1` 字段
2. 引入 `diff-match-patch` 依赖
3. 写 `NoteMerger.merge(base, local, remote) → { content, conflicts[] }`
4. SyncService 拉取时若版本号不一致 → 自动调 NoteMerger → 仍冲突则写 `note_conflicts` 表
5. UI 层监听冲突数量 → 顶部红点提示 → 弹出冲突预览 Dialog

**优先级：P0（多设备同步的核心保证）**

#### 3.3.7 流量控制与重试退避（借鉴 Blossom ⭐⭐）

**借鉴要点：** Blossom 集成 Sentinel 做 API 级别限流；Memocast 可在 Sync 层加指数退避。

**实施路径：**
- SyncService 包裹一层 `RetryWithBackoff`：失败时按 1s / 2s / 4s / 8s 退避，上限 30s
- WizNote API 调用间隔控制：每分钟 ≤ 60 次
- 主进程日志记录 sync 耗时，>5s 触发 warn（参考 Blossom 慢 SQL 思路）

**优先级：P1**

### 3.10 Blossom 专题：工程化与安全基线

> 本节集中处理 Blossom 文档中**与 Memocast 同属 Electron 体系**的工程化能力，是其它改进的前置或互补项。

#### 3.10.1 AI 模型 Key 加密存储（借鉴 Blossom ⭐⭐ P0）

**为什么值得借鉴：** Memocast 的 `ai_model_configs` 表当前以明文存储 API Key。Blossom 强调"对 API Key 做加密存储"，避免数据库泄露 → 云端 Key 泄露。

**实施路径：**
1. 引入 `crypto-js` AES-256
2. 主进程启动时从 `safeStorage`（Electron 13+）派生加密密钥
3. `ai_model_configs.api_key` 加密后存 SQLite
4. 读取时主进程解密 → 仅在内存中暴露给调用方
5. 监听 `safeStorage` 状态变化（macOS Keychain / Windows DPAPI）

**优先级：P0（AI 集成的基础安全）**

#### 3.10.2 数据目录密码保护（借鉴 Blossom ⭐⭐）

**借鉴要点：** Blossom 评估 SQLite 加密（sqlcipher）和目录密码保护机制。

**实施路径：**
- 评估 `sqlcipher`（更好-sqlite3 同形态）
- 或在主进程层做字段级加密（仅加密 `content`、`ai_model_configs.api_key`）
- 设置中加"启动密码"开关：每次启动需输入密码解锁 DB

**优先级：P2**

#### 3.10.3 多博客账号管理（借鉴 Blossom ⭐）

**借鉴要点：** Blossom 后端支持多博客账号（管理员/普通用户）。Memocast 未来可能需要"一个用户管理多个博客站点"。

**实施路径：**
- BlogDeployService 支持多个 `BlogDeployConfig`（每个配置绑定一个 repo / token / 域名）
- 设置中"博客部署"区块可增删改配置
- 笔记发布时选择目标站点

**优先级：P2（中期）**

#### 3.10.4 性能监控与慢查询日志（借鉴 Blossom ⭐⭐）

**借鉴要点：** Blossom 自研 `expand-tracker` 做链路追踪，`common-db` 做慢 SQL 监控。

**实施路径：**
- 主进程引入 `electron-log` 规范化日志
- SyncService 记录每次同步耗时，>5s 触发 warn
- SQL 层包装一层 `measureQuery()`：超过 200ms 记 warn 日志
- 设置页"日志查看"标签：实时显示 warn/error 计数

**优先级：P1（工程基线）**

#### 3.10.5 Pinia 试点 + Vue3 评估（借鉴 Blossom ⭐⭐ 长期）

**借鉴要点：** Blossom 用 Vue3 + Pinia + Element Plus + electron-vite。Memocast 当前 Vue 2.7 + Quasar 1.x + Vuex 3，已是历史栈。

**实施路径：**
- 短期：在新功能模块（如 BlogDeployDialog v2、备份服务 UI）试点 Pinia，与 Vuex 共存
- 中期：评估 Quasar 2.x（Vue3）升级成本
- 长期：评估是否保留 Quasar 或迁移 Element Plus（参考 Blossom 选型）
- 构建工具：评估 `electron-vite` 替换现有 webpack

**优先级：P2（长期）**

## 六、Memocast 差异化竞争策略

> 基于五款竞品分析，提炼 Memocast 未来 12-18 个月的差异化定位。

### 6.1 定位建议

> **"本地优先 · 块级双链 · 一键发布 · AI 可编排 · 工程化基线强 的工程师笔记平台"**

五款竞品的盲区：
- **Gridea-Pro**：本地优先但缺双链和块级能力，且无 Electron 安全基线意识
- **SiYuan**：块级双链很强但博客发布弱，云端门槛高
- **TriliumNext**：工程化做得好但博客、AI、移动端是短板
- **Yank Note**：AI 和程序员特性强但本地同步与冲突合并弱
- **Blossom**：工程链路完整、安全基线好，但缺乏博客自动化 + AI Copilot + 增量同步

Memocast 恰好横跨五者交集（写作 + 同步 + 博客 + AI + 工程化），可以做出"什么都有一点，但每一点都够用"的中庸而不平庸的产品。

### 6.2 四大差异化卖点

1. **本地的 WizNote 端到端加密同步 + 3-way merge 冲突合并 + 块级双链**（SiYuan 的安全 + Blossom 的合并 + Memocast 的体验）
2. **AI 可编排的工作流（MCP + 写作助手提示词 + Copilot + Key 加密）**（Gridea-Pro 的协议 + Yank Note 的补全 + Blossom 的 Key 安全）
3. **从笔记到博客一键打通 + SEO/评论/分享链接**（Gridea-Pro 的部署 + Blossom 的主题水印/分享链接）
4. **工程化基线（Electron 安全 + SpacedUpdate + SQLite 调优 + 慢查询日志）**（Blossom 的工程链路 + TriliumNext 的 SQLite 调优）

### 6.3 风险与边界

- **不与 SiYuan 正面竞争块级能力**：先做轻量 Block（段落级 ID），不复制 SQL 嵌入、IAL 全套，避免投入过深
- **不与 Gridea-Pro 正面竞争 SEO/部署平台数量**：先把现有 GitHub 部署做稳，SFTP/FTP 作为可选
- **不与 Yank Note 正面竞争代码块运行**：Electron 沙箱有安全风险，列为 P3
- **不与 TriliumNext 正面竞争多视图**：先做日历 + 思维导图，看板/Canvas 视用户反馈再投入
- **不与 Blossom 正面竞争多用户架构**：Memocast 定位单用户，多博客账号管理即可
- **始终坚持本地优先原则**：所有云端功能不污染 SQLite 主数据，云端仅做加密备份和发布通道

## 七、风险与注意事项

1. **技术栈差异**：SiYuan 用 Go、Gridea 用 Go、Trilium 用 Node、Yank Note 用 Electron。Memocast 是 Electron + Node.js + Vue2，部分借鉴项（如 Go Kernel、Lute 引擎）需找到 Node.js 等效实现（`isomorphic-git` / `better-sqlite3` / `tesseract.js`）。
2. **本地优先原则不变**：所有 AI / 云端功能均不影响 Memocast 现有的本地 SQLite 优先策略。云端仅为加密备份和发布通道。
3. **打包体积控制**：参考 Gridea，所有博客/插件/MCP 相关逻辑不打入主包，仅在用户启用时按需加载。
4. **Vue2 长期维护风险**：当前主项目 Vue 2.7.16 已停止官方维护，新插件系统设计时**避免强依赖 Vue2 特性**，降低未来升级 Vue3 的成本。
5. **依赖一致性**：借鉴项涉及的 npm 包（如 `@modelcontextprotocol/sdk`、`better-sqlite3`、`tesseract.js`、`excalidraw`）需逐个评估与现有 sql.js / crypto-js / shiki 等依赖的兼容性。
6. **不要照搬竞品的"为什么"**：每个产品都有它的取舍。Memocast 是 Memocast 的产品定位，借鉴的是"能力"，不是"产品形态"。
