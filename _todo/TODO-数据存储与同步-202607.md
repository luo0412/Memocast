## 一、当前现状（2026-07-17 视角）

### 1.1 笔记存储：仍为单一 SQLite

- 所有笔记内容保存在 `memocast.db` 的 `notes.content` 字段中（Markdown 文本）。
- 已有的 `SessionStorageService` 是**浏览器 session/localStorage 抽象**（账号信息、token 等），与本文档讨论的"存储机制"无关，命名易混淆。
- `notes.content_file` / `notes.storage_mechanism` / `notes.content_yjs` / `notes.has_conflict` 等字段**均不存在**。
- `conflict_log` 表**不存在**。

### 1.2 同步：仍为本地覆盖云端（LWW 变种）

- `SyncService.pushToCloud()` 已有的本地优先 + dirty=1 机制完全保留。
- **没有冲突检测**：本地永远覆盖云端（拉取仅做"新建本地缺失的云端笔记"，不主动合并已存在笔记）。
- 没有 Yjs / CRDT / OT / Vector Clock 等任何智能合并层。

### 1.3 相关的真实代码入口

| 路径 | 现状 |
|------|------|
| `src/services/SyncService.js` | 推送/拉取主干逻辑，**无冲突分支** |
| `src/services/CloudSyncService.js` | UI 层同步状态封装 |
| `src/store/server/actions.js` → `getNoteContent` / `updateNote` | 笔记读写主干；从 SQLite 读，云端兜底 |
| `src/utils/DatabaseClient.js` | 渲染进程数据库客户端 |
| `src-electron/main-process/electron-main.js` | SQLite + IPC handlers（无 storage / conflict / yjs 相关 handler） |
| `package.json` | 不含 `yjs` / `y-indexeddb` / `y-websocket` / `diff-match-patch` / `js-yaml` |

#### 待决策

- ❓ **是否真有必要做 MD 文件存储？**
 - 论据（支持）：数据可被外部工具（VS Code、Obsidian、Syncthing）直接读写；和博客打包流程复用；做 Obsidian/Logseq 兼容
 - 论据（反对）：当前 SQLite 同步到 WizNote 已经满足多端；引入 MD 会**两套内容双写**（SQLite `content` + 文件正文），文件 I/O 在主进程大量调用；front-matter 与分类树的双向同步有边界 case
 - **目前 Memocast 没有强烈的"要在外部编辑器打开笔记"需求**

- ❓ **`SessionStorageService` 命名是否调整？** 这是一个长期易混淆项，但**与本议题无关**，不应混入本 TODO。

#### 若决定要做，需解决的关键问题（前提）

> 历史方案里以下问题已经讨论过，但因本议题尚未启动，先只列决策点：

- 引入新字段（`content_file`, `storage_mechanism`）后，是否允许单笔记"混合"——同一笔记库中部分 MD / 部分 SQLite？
- 切换机制时是否一次性迁移，还是按笔记懒迁移（默认方案倾向一次性 + 备份）
- MD 模式下 sync（推送/拉取）是否需要感知存储机制？倾向**否**：`content` 字段同步期间仍缓存完整文本以保持 WizNote API 兼容

### B. 云端同步冲突解决

> 来源：`TODO-本地线上文件冲突合并-202608.md`
> 状态：🔴 **未开始**

#### 待决策

- ❓ **是否启动 Phase 1（轻量冲突感知）？**
 - 论据：单用户多设备场景下确实会出现"两端都改"；当前实现直接覆盖会丢数据
 - 论据：当前 WizNote 备份只推送不主动拉取合并，冲突仅出现在**再次拉取恢复**时，频次不高
 - **当前产品阶段不阻塞**，可缓后

- ❓ **是否启动 Phase 2（Yjs / CRDT）？**
 - 调研结论保留：Yjs 是同时解决"单用户多设备合并"和"未来协同"的最佳工具
 - 但**当前 Memocast 没有协同需求**——只有同一个 WizNote 账号下的多设备备份
 - 历史文档已记录的判断（2026-06）：「不要因为明年才协同就跳过 CRDT，引入成本不高」
 - 待重新评估：是否仍成立？同步工具栈的整体方向（WizNote → 是否换？自建？）

- ❓ **WizNote API 是否会扩展支持 CRDT / 字段扩展？**
 - 历史文档论断：**不可以自定扩展**——这意味着 Phase 2 Yjs Update 必须自建 Gateway 或转用其它云端
 - 若上云端策略长期不变，Yjs 落地的实际收益只剩"本地富文本合并"

- ❓ **路径三（TipTap 替换 Muya）？** —— ⚪ **明确弃用**。Muya 是 Memocast 编辑器核心依赖，替换成本极高，无业务强驱动。

- ❓ **路径四（自建 CRDT Gateway）？** —— ⚪ **明确推迟**。需要独立服务 + 运维成本，背离本地优先 + WizNote 备份的当前架构。

## 四、历史背景（保留要点）

> 这里只保留**结论性背景**，便于后续决策时无需重新调研。所有具体代码/字段/路径等执行细节已被精简掉，需要时按议题新建小 TODO 重新整理。

1. **当前同步模型的本质**：`本地优先 + LWW + 手动触发`，依靠 `dirty=1` 把待同步笔记推到云端。
2. **冲突在 Memocast 场景的精确定义**：同一账号在不同设备上分时编辑同一笔记，重新拉取/同步时本地内容被覆盖。**非多用户实时协同**。
3. **CRDT vs LWW**：LWW 在快速连续编辑场景（< 1s）会丢数据，CRDT 保证不丢且能自动合并非冲突区域。
4. **Yjs 生态现状（2026 调研）**：Yjs 是 Notion 底层；`@muya/integration-yjs` 存在但未验证质量；`y-indexeddb` Provider 天然匹配本地优先。
5. **MD 文件存储的设计哲学**：单笔记双写（DB 缓存 + 文件正文），可逆切换，按笔记归属机制（不强制批量切换）。
6. **WizNote API 兼容性结论**：不支持 Yjs 二进制语义，需 Gateway 或字段扩展——这是两个 Phase 共同的最大阻力点。
