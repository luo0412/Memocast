# Vue3 升级迁移成本调研

> 调研日期：2026-08-18  
> 范围：Coolma 当前 Vue 2.7 + Quasar 1 + Electron 技术栈是否适合升级到 Vue3，以及如果升级应采用什么技术路线。  
> 产品前提：Coolma 当前更重要的目标不是做一个“标准而完整”的笔记软件，而是做一个**邪门但好玩、能截图传播、能让别人也玩起来的网红笔记项目**。  
> 结论先行：**现在不适合做全量 Vue3 升级；适合把 Vue3 放到长期预案，同时优先保护“邪门但好玩”的新功能迭代速度。**

---

## 0. 一句话结论

当前不建议把 Vue3 升级作为近期主线，尤其不应让它阻塞 README 中这类新功能：

- `ikun历险记`
- `小怪兽删除`
- `从夯到拉`
- Echo / Rune 的可编程笔记玩法
- 在线 Demo、远程 Rune 导入、可分享的 JSON 模板

这些功能的传播价值来自“反常识、好玩、容易展示”，不是来自底层框架版本。

原因不是 Vue3 不好，而是 Coolma 的迁移成本不在普通 Vue 组件层，而在：

1. **Quasar 1 → Quasar 2/3 构建链重迁移**
2. **Element-UI / Ant Design Vue 1.x / form-create 等 Vue2 UI 生态替换**
3. **Muya + rune 动态 SFC 渲染链路重写**
4. **wujie-vue2 / Vuex3 / vue-router3 / vue-i18n8 等基础设施整体升级**
5. **Electron 打包与 Webpack4/Vite 迁移风险叠加**

如果现在全量升级，预计会消耗 **1 人 8-12 周起步**；若同时切 Vite、替换 UI 库、修 Electron 安全模型和完整 QA，实际更接近 **12-16 周**。这段时间会明显挤占云函数同步、笔记体验、AI/echo/rune 等产品能力。

建议：

- **近期：不升主线**，继续保持 Vue 2.7 + Quasar 1；
- **同时：开始 Vue3 预迁移治理**，把新增代码写成更易迁移的形态；
- **中期：建独立 `vue3-migration-spike` 分支**，只验证最小闭环；
- **触发条件满足后再正式迁移**：如核心依赖停止可用、招聘/维护压力明显升高、或 Web 端化/插件生态必须依赖 Vue3。

- Vue Router 迁移指南：https://router.vuejs.org/guide/migration/

关键理解：

- Vue3 官方提供 `@vue/compat`，适合老项目渐进迁移，但对依赖 Vue2 内部 API 或未公开行为的第三方库有限制。
- Vue Router 4 不是类式 `new VueRouter()`，而是 `createRouter()` + `history` 配置。
- Vuex 4 可以支持 Vue3 且 API 与 Vuex 3 基本接近，适合作为过渡；不应在第一轮同时强转 Pinia。
- Quasar 当前主推 Vite 体系；Webpack 体系已进入维护/修复状态，不再是长期新增能力方向。

## 2. 迁移收益

### 2.1 真收益

| 收益 | 价值 |
| --- | --- |
| 生态回到主流 | 新 UI 库、文档、招聘、社区方案更集中在 Vue3 |
| 更好的 TS/IDE 体验 | `<script setup>`、Volar、类型推断更现代 |
| 更好的长期维护性 | Vue2 已 EOL，Vue3 是长期主线 |
| 构建现代化 | 若顺带迁到 Vite，开发启动、HMR、依赖处理更舒服 |
| 组合式 API | 复杂状态逻辑可以抽 composable，但 Options API 仍可保留 |
| 部分性能收益 | Vue3 runtime 更轻，响应式/编译优化更好；但不一定解决 Coolma 当前真实瓶颈 |

### 2.2 对 Coolma 的有限收益

Vue3 并不会直接强化以下核心能力：

- 本地优先 SQLite 同步；
- 云函数 Provider 抽象；
- Muya 编辑器体验；
- rune / echo 的产品玩法；
- AI 编排；
- Electron 安全模型；
- WizNote / 新云同步迁移。

也就是说，Vue3 是长期工程质量收益，不是近期产品突破口。对网红笔记项目而言，Vue3 更像“后台基础设施升级”，而 Echo/Rune、视觉效果、在线 Demo、模板分享才是“前台内容”。

### 2.3 “邪门但好玩”是当前产品目标

当前产品不应把自己包装成另一个 Notion、Obsidian 或思源笔记，而应明确保持以下方向：

```text
普通笔记作为底座
邪门的语法作为入口
好玩的交互作为记忆点
可截图/可录屏作为传播素材
可导入/可 Fork 作为扩散机制
```

因此，技术决策应优先回答：

1. 新功能能不能更快做出来？
2. 用户能不能一眼看懂并产生“这是什么东西”的好奇心？
3. 能不能通过 README、GIF、在线 Demo 或 JSON 模板复现？
4. 能不能让其他人改出自己的版本？

如果 Vue3 升级不能直接提升这四项，就不应抢占当前主线资源。

## 3. 迁移成本拆解

### 3.1 低到中成本：常规 Vue2 写法替换

这些可以通过预迁移阶段慢慢改：

| 项目 | 做法 | 成本 |
| --- | --- | --- |
| `.sync` | 改为 `v-model:xxx` / `@update:xxx` | 中 |
| `.native` | 改为组件显式 `$emit` 或透传 listener | 低-中 |
| `slot-scope` | 改 `v-slot` | 低 |
| `beforeDestroy/destroyed` | 改 `beforeUnmount/unmounted` | 低 |
| `Vue.prototype` | 聚合到 app plugin / globalProperties 适配层 | 中 |
| `new Vue()` event bus | 包一层 event emitter，底层换 `mitt` | 中 |
| Vuex3 | 先 Vuex4，保留模块结构 | 中 |
| Router3 | 改 `createRouter` / `createWebHashHistory` | 中 |
| i18n8 | 先用 vue-i18n 9 legacy 模式 | 中 |

### 3.2 高成本：UI 库替换

当前不是单一 Quasar 项目，而是：

- Quasar 1
- Element UI 2
- Ant Design Vue 1
- form-create element-ui 版
- form-create ant-design-vue 版
- vue-element-ui-x

这意味着升级不是“换 Vue 核心包”，而是多个 UI 生态同时断代。

建议不要一次把 UI 全部改为一种库。可选路线：

| 路线 | 说明 | 判断 |
| --- | --- | --- |
| Quasar 2 为主，Element/Ant 保留最小兼容替换 | 最接近现状，但需要找到 Vue3 版组件替代 | 推荐 |
| 全面转 Element Plus | 工作量巨大，Quasar 布局和插件要重做 | 不推荐 |
| 全面转 Ant Design Vue 4 | 同样巨大，桌面笔记软件风格不一定合适 | 不推荐 |
| 关键新弹窗用 Vue3 子应用，老 UI 不动 | 可做过渡，但复杂度上升 | 只适合 PoC |

### 3.3 最高风险：Muya / rune 动态 SFC 链路

这是本项目区别于普通 Vue2 应用的最大迁移难点。

当前关键路径：

- `src/components/muya/Muya.vue`
  - 使用 `Vue.extend` 定义 `RunePreviewRenderer` / `EchoPreviewRenderer`
  - 通过 render function 把 rune/echo host 挂进 Muya 产物
- `src/components/muya/runeSfcRendererFactory.js`
  - 使用 `vue-template-compiler`
  - `parseComponent`
  - `compileToFunctions`
  - 输出 `Vue.extend(...)` 构造器
- `src-electron/main-process/service/vueSfcCompilerService.js`
  - 使用 `@vue/compiler-sfc@2.7.16`
  - 给微应用 / playground 做 SFC 解析
- rune 模板与测试
  - `tests/unit/rune/*`
  - `tests/unit/muya/rune-sfc-cache.test.js`

Vue3 后需要重做：

| 当前 | Vue3 目标 |
| --- | --- |
| `Vue.extend({...})` | `defineComponent({...})` 或普通组件对象 |
| `new Vue()` 挂载局部实例 | `createApp(component).mount(el)` 或 `render(vnode, el)` |
| `vue-template-compiler.compileToFunctions` | `@vue/compiler-dom` / `@vue/compiler-sfc` 生成 render |
| Vue2 render function data 格式 | Vue3 `h()` / VNode props 格式 |
| `$emit('input')` | `emit('update:modelValue')` 或兼容桥 |
| scoped style 注入 | 重新校验 scopeId 与 runtime DOM 的关系 |

这个链路不能靠普通 codemod 解决，必须单独设计。

可选方案：

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| A. 原地重写为 Vue3 renderer | Muya 仍在主应用，rune 编译输出 Vue3 组件 | 长期最干净，短期最高风险 |
| B. rune 渲染做 Vue2 island | 主应用 Vue3，rune/echo 预览用隔离 iframe / micro-app 运行 Vue2 | 迁移风险低，但架构更复杂 |
| C. 暂停动态 SFC，只保留内置 rune | 先把用户自定义 SFC 关掉或降级 | 产品损伤大，不推荐 |
| D. 独立 Web Component runtime | rune 编译成自定义元素 | 长期漂亮，但研发成本最高 |

如果将来正式升级，推荐先验证 **A**；如果 A 卡住，再用 **B** 兜底。

## 4. 技术路线建议

### 4.1 不建议的路线

不要一把梭：

```text
Vue2 + Quasar1 + Webpack4
  → Vue3 + Quasar最新版 + Vite + Pinia + Element Plus + Electron 安全模型重构
```

这会把框架升级、UI 替换、构建迁移、状态管理迁移、编辑器 runtime 重写、Electron 安全改造全部压在同一条线上，排障会非常痛苦。

### 4.2 推荐路线：主线不动，旁路 PoC

#### Phase 0：预迁移治理，不升版本

目标：让当前 Vue2 代码更像 Vue3 兼容代码。

任务：

- 新代码禁止使用 `.sync`、`.native`、`slot-scope`；
- 新弹窗组件不再写 `model:` 选项，改显式 `value/input` + 兼容注释；
- 把 `Vue.prototype.$xxx` 收敛到一个 `global-adapter`；
- 把 `new Vue()` event bus 封装成 `eventBus.emit/on/off`，隐藏实现；
- boot 文件避免继续散落全局副作用；
- 新服务层避免依赖组件实例上的 `this.$store` / `this.$q`；
- 继续补 smoke/unit 测试，尤其是 Muya/rune/echo/同步。

预计成本：**1-2 周**，可以穿插在日常开发中。

#### Phase 1：Vue3 migration spike 分支

目标：不追求可发布，只判断“升 Vue3 是否能跑通最小闭环”。

建议分支：

```text
codex/vue3-migration-spike
```

验证范围：

```text
启动 Electron
打开主界面
打开设置框
显示笔记列表
打开一篇笔记
Muya 正常渲染 Markdown
编辑并保存
14 个内置 rune 模板至少渲染一轮
echo 占位符能点击/提交
云函数设置框仍可保存配置
Windows dev build 能启动
```

预计成本：**1-2 周**。

退出标准：

- 若 Muya/rune 动态 SFC 3 天内无法跑通最小渲染，暂停正式迁移；
- 若 UI 库替换导致 30% 以上页面无法编译，暂停正式迁移；
- 若 Electron 打包链需要同时重写，迁移拆成两阶段。

#### Phase 2：兼容构建优先，不转 Pinia

如果 Phase 1 通过，正式迁移第一阶段仍不建议转 Pinia。

技术选择：

- Vuex 3 → Vuex 4，保留模块结构；
- Vue Router 3 → Vue Router 4/5；
- vue-i18n 8 → vue-i18n 9 legacy；
- Options API 继续保留；
- `@vue/compat` 作为短期迁移辅助；
- Quasar 优先上 Vue3 可用版本；
- Vite 是否同步切换，单独评估，不作为 Vue3 成败前置条件。

预计成本：**3-5 周**。

#### Phase 3：UI 库替换与组件修复

任务：

- Element UI → Element Plus 或替换为 Quasar 等价组件；
- Ant Design Vue 1 → Vue3 版；
- form-create 换 Vue3 对应包；
- vuedraggable / scrollbar / layerx / clamp 替换；
- 全量修复 `.sync` / `.native` / slot / v-model / 生命周期；
- 更新测试工具链：`@vue/test-utils@2`、Jest transformer 或迁 Vitest。

预计成本：**3-6 周**。

#### Phase 4：Muya / rune / echo runtime 重写

这是决定能不能发布的核心。

任务：

- 将 `RunePreviewRenderer` / `EchoPreviewRenderer` 改为 Vue3 component；
- 重写 `runeSfcRendererFactory`；
- 设计 Vue3 版动态 SFC 编译缓存；
- 保留旧 `input` 事件兼容，外层统一转为 `update:modelValue`；
- 验证 scoped style、组件销毁、内存回收；
- 跑 14 个内置 rune 模板 + 用户导入 rune pack；
- 对大文档做性能测试。

预计成本：**2-4 周**。

#### Phase 5：去 compat + 打包发布

任务：

- 逐步关闭 `@vue/compat` flags；
- 修复剩余 runtime warning；
- 构建 Windows/macOS/Linux；
- 验证自动更新、SQLite、云同步、导入导出、插件、微应用；
- 准备回滚包。

预计成本：**1-2 周**。

## 5. 当前是否适合升级

### 5.1 判断表

| 判断项 | 当前状态 | 结论 |
| --- | --- | --- |
| 产品主线是否需要 Vue3 才能推进 | 云函数同步、轻量任务、AI、笔记体验都不依赖 Vue3 | 不支持立即升级 |
| 当前 Vue2 是否已经阻塞开发 | 暂未看到硬阻塞 | 不支持立即升级 |
| 安全风险是否只能靠 Vue3 解决 | 不是，更多在 Electron、XSS、依赖审计、UI 库维护 | 不支持立即升级 |
| 迁移收益是否足以覆盖 2-4 个月机会成本 | 目前不足 | 不支持立即升级 |
| 迁移风险是否可控 | Muya/rune 动态 SFC 未验证前不可控 | 不支持全量升级 |
| 是否需要为未来做准备 | 是，Vue2 EOL 和生态老化是真风险 | 支持预迁移治理 |

### 5.2 最终结论

**当前不适合全量升级 Vue3。**

更准确地说：

```text
不适合：把 Vue3 升级作为近期主线、一次性替换整栈。
适合：开一个 PoC 分支做可行性验证，并在主线持续清理 Vue3 不兼容写法。
```

推荐优先级：

1. **优先做“邪门但好玩”的可传播功能**：Echo、Rune、视觉交互、梗玩法、在线 Demo；
2. 把 README 从功能清单升级成作品橱窗：截图、GIF、演示链接、一键导入模板；
3. 推进 Rune/Echo 模板分享和轻量生态，让别人能 Fork、改造和投稿；
4. 继续推进云函数同步 MVP，但只做到够用，不让后台工程吞掉前台创意；
5. 加强 Electron 安全模型、依赖审计、XSS 防护；
6. 做 Vue3 预迁移治理和独立 PoC；
7. 只有在 Muya/rune Vue3 链路跑通后，再排正式升级。

## 6. 决策触发条件

满足任一条件时，再把 Vue3 正式升级提到主线：

1. **核心依赖断供**：Quasar 1 / Element UI / wujie-vue2 / vue-i18n8 出现无法规避的安全或兼容问题；
2. **新能力强依赖 Vue3**：某个必须接入的插件、AI UI、编辑器 runtime 只支持 Vue3；
3. **招聘与维护压力变大**：Vue2 维护者显著难找，新增功能开始明显变慢；
4. **计划 Web 端化**：如果 Coolma 要从 Electron 桌面扩到 Web/PWA，Vite + Vue3 的收益会明显上升；
5. **Muya/rune PoC 成功**：动态 SFC 渲染链路已在 Vue3 分支跑通，最大未知被消除。

## 8. 技术方案备忘

### 8.1 目标版本建议

正式升级时建议目标：

```text
Vue 3.x
Quasar 2/3（按当时稳定版选择）
Vue Router 4/5
Vuex 4 过渡，后续再考虑 Pinia
vue-i18n 9+ legacy 过渡
Element Plus / Ant Design Vue 4 按实际组件需求替换
@vue/test-utils 2
```

不建议第一轮就强制：

```text
全量 TypeScript
全量 Composition API
全量 Pinia
全量 Vite
完全移除 Options API
重写所有 UI 组件
```

这些都是好东西，但不该和第一轮 Vue3 升级绑死。

### 8.2 最小回滚策略

正式迁移必须满足：

- 保留 Vue2 主线可发版；
- Vue3 分支不与云函数同步 MVP 混在同一大 PR；
- 每个阶段都有可运行检查；
- 所有数据库迁移与同步协议不绑定 Vue3；
- 失败时只回滚前端壳，不影响本地笔记数据。

### 8.3 最小验收标准

正式宣布“Vue3 可迁”的最低标准：

- [ ] Electron dev 正常启动；
- [ ] Windows build 产物可运行；
- [ ] 设置框所有 tab 可打开；
- [ ] 登录/服务器配置不丢；
- [ ] 笔记列表、分类树、标签/搜索基本可用；
- [ ] Muya 打开、编辑、保存无数据损坏；
- [ ] rune 内置 14 个模板可渲染；
- [ ] echo 可点击、提交、回写；
- [ ] 云函数设置框 provider 配置可保存；
- [ ] 核心单测/冒烟测试通过；
- [ ] 无明显内存泄漏和控制台错误风暴。

## 10. 结论

Vue3 是 Coolma 的长期方向，但不是当前最该打的仗。当前最重要的不是把项目变得“更标准”，而是把它变得**更邪门、更好玩、更容易被看见和转发**。

当前更优解：

```text
主线继续 Vue2.7
优先做邪门但好玩的 Echo / Rune 新功能
把 README / Demo / 模板分享做成传播入口
云函数只做到够用，服务同步和轻量任务
同时清理 Vue3 不兼容写法
用独立分支验证 Muya/rune 能不能迁
等产品传播势能和迁移可行性都成熟后再正式排期 Vue3
```
